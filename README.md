*Formerly “Demand Planning Hub”. The desktop installer and its update feed keep their file names (`Demand-Planning-Hub-Setup.exe`, `Demand-Planning-Hub-mac.dmg`) so installed apps keep updating.*

Requires Node.js and pnpm.




### Desktop downloads

CI packages a Windows installer (`Demand-Planning-Hub-Setup.exe`, on `windows-latest`) and a universal macOS disk image (`Demand-Planning-Hub-mac.dmg`, on `macos-latest`) (the Windows installer for every pull request and push; the macOS image, whose runners often queue, only for pushes to `main`, tags and manual runs). On each push to `main`, **Publish Windows installer** and **Publish macOS installer** run separately, each as soon as its own package is ready, and upload it with its SHA-256 checksum to one rolling GitHub pre-release tagged `desktop-latest`, replacing the previous file. `latest.json` keeps a build number and revision per platform (`scripts/desktop-manifest.cjs`); its top-level build number is the oldest of them, so apps from before this change only see an update once both installers are published. The fixed file names give stable links, which the app's **⬇ Desktop app** button (sidebar) offers, highlighting the one for the visitor's operating system:

- Windows: `https://github.com/neurolooom-eng/Test2/releases/download/desktop-latest/Demand-Planning-Hub-Setup.exe`
- macOS: `https://github.com/neurolooom-eng/Test2/releases/download/desktop-latest/Demand-Planning-Hub-mac.dmg`

**Updating the desktop app from the app.** The desktop app also checks quietly at start and every 4 hours; when a newer build is published it shows an **Update available** notice (bottom right, every page) with **Update now** (opens the update dialog) and **Later** (hides it until the next newer build). The sidebar's **↻ Check for updates** button (desktop app only) reads `latest.json`, which the publish job uploads next to the installers (build number = the CI run number the app shows, revision, and each installer's size and SHA-256). When the published build number is higher than the installed one, **Download and install** fetches only this platform's installer from the fixed `desktop-latest` address, verifies size and SHA-256 (a mismatch deletes the file and installs nothing), then on Windows starts the installer and closes the app, and on macOS opens the disk image to drag the app into Applications. Saved data and PATs live in the user profile and are kept. The same backup / unsaved-work checks as Force Update apply first. The check needs the repository's releases to be publicly downloadable; with a private repository it reports that no published build was found. Desktop builds made locally carry their Git commit count as build number and may not see CI builds as newer.

The installers are not code-signed or notarised (no certificates are configured): Windows SmartScreen asks for *More info → Run anyway*, and macOS needs *right-click → Open* the first time (or `xattr -cr "/Applications/Demand Planning Hub.app"` if it reports the app as damaged). Signing needs a Windows code-signing certificate and an Apple Developer ID, added as repository secrets. Version tags `v*` still create a versioned release as before.

## GitHub Actions deployment

### Versions, build identity and Force Update

The authoritative version is `package.json` (`x.y.z`); the UI and release tags use **vX.Y.Z**, and [docs/RELEASE-NOTES.md](docs/RELEASE-NOTES.md) is the version history (newest first). **Every merged change gets a version**: its pull request adds a change note in `docs/changes/` (see [its README](docs/changes/README.md)) naming the bump — **X** for a change that breaks existing data, shared setup files or the way users work (reset Y and Z), **Y** for a new or changed feature (reset Z), **Z** for a fix, a dependency update or documentation only — and its release-notes text. After the merge, CI's release commit sets the version in `package.json`, writes the entry (with the PR number) at the top of the release notes and regenerates the SWBOM and the traceability matrix, so open pull requests do not conflict on them. `pnpm test` fails on a malformed note or when the newest release-notes version is not the package version. CI tags each version `vX.Y.Z` on its release commit and publishes its GitHub release (installers, checksums and the release-notes entry) — nobody tags by hand; a rebuild of an unchanged version keeps its version and gets a new build ID. How versions, builds, tags, baselines and the shared setup are controlled is in [docs/CONFIGURATION-MANAGEMENT.md](docs/CONFIGURATION-MANAGEMENT.md).

The sidebar shows version, build ID and build date/time in **IST**; the Force Update dialog also shows the source commit. GitHub Actions stamps the build ID as `GITHUB_RUN_ID.GITHUB_RUN_ATTEMPT` and the build number as `GITHUB_RUN_NUMBER`; local builds use a commit/timestamp ID and the commit count. The version stays fixed between releases; the build number is the internal reference for which deployment is running. Metadata is embedded in the app, emitted to `build-info.json`, and stamped into HTML. Both CI jobs verify the version and reject a release tag that does not exactly match `v` plus the package version.

**Force Update** checks a cache-busted, `no-store` build manifest, retrieves fresh same-origin HTML, verifies that its build ID matches the manifest, then navigates using unique update query parameters. Hashed assets include the build metadata and therefore change with each build. An offline/error response or an older HTML response blocks navigation and allows retry. This is a supported best-effort web equivalent of Ctrl+Shift+R; web JavaScript cannot invoke the browser's privileged hard-reload command. The button never clears localStorage, IndexedDB, cookies, PATs or column preferences. Browser/proxy caching policies still apply.

Updates always require acknowledgment of unfinished forms. Pending saves and active Azure fetches block reload. A failed save or unsaved fetched preview requires exporting JSON first; the update backup includes the current preview and its scope. Export does not capture text in unsubmitted forms, so save or cancel those first. Desktop **Force Update** uses a trusted, narrow Electron cache-ignoring reload and reloads the installed package only—it does not download/install a new executable. The web button is also available on the startup/recovery screen, where it never exports an unread dataset as if it had been loaded.

Every push or pull request to `main` runs static analysis, compiles the production web bundle, packages the Windows NSIS installer, calculates its SHA-256 checksum and publishes the result as a 30-day workflow artifact.

Pushing a version tag such as `v0.1.0` runs the same verified pipeline and deploys the installer, blockmap and checksum to a GitHub Release. The workflow uses the repository-scoped `GITHUB_TOKEN`; no personal access token or application secret is required.

Every push to `main` also builds and deploys the browser version to GitHub Pages at `https://ponkritz.github.io/DemandPlanning/`. It uses local browser storage; shared data goes to the Git data repository once Git storage is connected (Admin → Data & sharing → Git storage).

## Data and security boundary

### Azure dashboard mapping (v1.0.0)

**Team / Individual.** Pulse Check → Last month has a switch: **Team** shows everyone; **Individual** shows one person (defaults to you; any other assignee can be picked), keeping that person's Tasks plus the public holidays of their region. Dashboard uses its **Team member** filter instead. The choice is remembered in this browser.

Dashboard and its deterministic insights consume the exact same scoped `azure.items` workspace as Backlogs: a fresh selected-team preview takes precedence over the verified saved cache. Removed records are excluded. Visual state filters on Backlogs do not change dashboard totals. Refresh is explicit; failed refreshes retain the previous dataset and display the error. There is no local planning/demo fallback.

The selected month Task is the authoritative source: `Microsoft.VSTS.Scheduling.OriginalEstimate` and `Microsoft.VSTS.Scheduling.CompletedWork` are read directly from a Task named, for example, `October 2026 | Feature title`. Its parent story provides context only. Missing Task fields remain unavailable; zero remains zero; populated-field counts are displayed. Variance uses only Tasks with both fields. The >25% alert compares Completed Work to a positive Original Estimate, not a separately approved baseline. **Monthly Time Writing** stages edits across multiple Tasks and saves them in one controlled action. Each changed Task is re-read and must still be a Task whose title starts with a month and year, then Azure confirms the exact saved field(s); the action requires the active ADS configuration PAT to have Work Items (Read & Write). It cannot edit Features, arbitrary fields or another project.

The six-month table uses Original Estimate and Completed Work only on month-named Tasks (see **Time Writing naming**), assigned to months by the month and year at the start of the title. The dashboard and Monthly Time Writing view group these selected stories by traversing Story → Feature → Epic parent links. Items without a resolved Epic appear as `No Epic path`. Undated/unmatched tasks are counted as unmapped, not attributed by Created/Changed Date. Work-field units must be confirmed in the Azure project; Story Points are never treated as hours. Snapshot/revision history is not available, so estimates are not claimed to be frozen monthly plans or time entries.

NPRA Hours remain a separately tracked Feature category (exact tag `NPRA Hours`) and do not adjust utilization. Weekdays only are counted as working days (Monday–Friday). Regional public holidays come only from the absence Epic (see below); partial availability and leave booked outside the absence Epic are not inferred.

### Capacity, absence and utilization

The capacity view on **Pulse Check → Last month** is built from a capacity model (`src/capacity.ts`) over that month's Time Writing Tasks; the Dashboard uses the same capacity (working days, hours per day, absence, holidays) per person and month, with the thresholds below as its utilization bands. Funded hours per person are `working days × hours per day` (default 8). **Absence** is the Completed Work on month Tasks whose Epic is the configured **absence Epic** (default `#37778`); each person's Feature under that Epic, and the Task title, decide whether the hours are **PTO**, **Sick Leave** or **Unplanned Leave** (anything else is "Other absence"). **Utilization = Utilized hours ÷ (Contractual hours − Absence hours) × 100** (CAP-38, v4.0.0): Contractual hours = working days employed × hours per day; Absence hours = PTO + Sick Leave + Unplanned Leave + public holidays + other absence; Utilized hours = Work + Trainings + Other NPRA + Common activities (Completed Work; Planned utilization uses Original Estimate). Trainings, other NPRA and common activities are no longer deducted from capacity; the team figure adds up the people. Pulse Check → Last month shows each person's Contractual, Absence, Available, Work, Trainings, Other NPRA, Common activities, Planned, Utilized and Utilization; Team overview shows the same split in Capacity and workload → Workload by person (over the period) and in its **Utilization** tab (one month, CAP-39). A person is **Overloaded** at or above the overloaded threshold (default 100 %) and **Has capacity** below the capacity threshold (default 80 %); in between is Balanced; a person with absence only is "No bookings". Streams are the Epics reached by walking Task → Story → Feature → Epic; the person × stream matrix shows booked hours per Epic. The absence Epic ID, hours per day and both thresholds are edited under **Settings → Capacity and absence** and stored with the shared app data (IndexedDB, shared through Git), not per browser; every change is audited. An empty or zero denominator displays unavailable rather than an infinite percentage.

**Release baselines.** The **Baselines** page calculates each release's baseline from **estimation rules** per stream (`src/baseline.ts`): fixed hours by release type (e.g. DP Major 40h, MLD 30h, PU 20h), plus line items priced per unit where *units = base units + driver count × units per driver* (e.g. CP documents: `2h × (14 + 11 × assets)`), with an optional maximum per release (e.g. Serviceability 60h). Releases are the Features under a stream Epic that has a rule. Each release's scope (type and driver counts such as documents or assets) is kept as a dated history: re-baselining after items are scoped in adds a version, so the page shows the first baseline, the current one, the scope growth between them and the actual Completed Work booked on the release's Time Writing Tasks. The rule values shipped are illustrative examples to be replaced with the exact baseline. Rules, scopes and the resource mapping are saved to Git (below).

**Time Writing naming.** The month Task is the anchor, not its story. A Task counts for a month when its title starts **or ends** with the month and year, with any delimiter or none (`October 2026 | …`, `Oct 2026 - …`, `2026-10 | …`, `… | October 2026`, `… - Oct 2026`, `… (October 2026)`, `… 2026-10`). A month in the middle of a title is not used, and a leading month wins if both are present. The User Story above it can have any name — the Feature and Epic (stream) come from the parent links, and a month Task directly under a Feature counts too. A story is treated as a Time Writing story when it holds a month Task or its title says "Time Writing". The rules live in `src/azureInsights.ts` (`timeWritingMonth`, `isMonthTask`, `timeWritingStoryIds`, `planMonthStory`) and are shared by every page. Monthly Time Writing ends with a **Not picked up** check listing open Time Writing stories without the month's Task, Tasks under a Time Writing story without a month prefix (not counted), and month Tasks with no Feature above them (counted, but without a stream). When My work creates your month Task it reuses any month Task of yours under the Feature (any title), and otherwise picks the story titled `<Feature> - Time Writing`, else the story already holding your month Tasks, else the Feature's only Time Writing story; with several candidates it stops and asks you to add the Task in Azure DevOps.

**My Tasks [Board].** The **My Tasks [Board]** page (with a pending count in the sidebar) lists the New / Active items assigned to you — matched by the Time Writing connection's Feature creator email (Azure *Assigned To* unique name), or by a display name chosen on the page — excluding the absence Epic. One **search box** looks through every type at once (ID with or without #, title, type, state, Feature, Epic, Area Path, Iteration Path, tags; every word must match, any order or case); Esc or a type chip clears it. **＋ New Feature** opens the board's *Add Feature under an Epic* editor (Epic selectable) and **Complete children** on a Feature row that has no optional User Story yet (the Time Writing story does not count) adds its missing User Stories and this month's Time Writing task. A **▸ on a Feature** expands it one level: its User Stories (and anything placed straight under it); a **▸ on a User Story** then shows its Tasks. Items of everyone are shown, with state, iteration and, for Tasks, planned and recorded hours; your own New or Active items keep their Close action there. The list's rules are behind **ⓘ Info** next to its title (hover, focus or tap) — as on every page: explanations of how a list, chart or rule works sit behind ⓘ Info next to their heading, while counts, fetch times and totals stay visible. From there you can:
- **Close an item**: **Close User Story / Epic / Task / Bug** (by the item's type) sets its State to Closed after confirmation. A User Story in **New** offers **Set User Story to Active** — which also makes its Feature Active when the Feature is New; a **New Feature** offers **Set Feature to Active** only when one of its User Stories is Active (else “Set a User Story to Active first”); only an **Active** one offers **Close …** (other states say “Set to Active first”). Azure DevOps refuses a change its process does not allow, and the error is shown. After **Close Feature** the page asks whether to also close its open User Stories (listed in the prompt); after the last open User Story of a Feature is closed it asks whether to also close the Feature. Confirmed, they are closed one by one in the same staged order; declined, nothing more is written.
- **State checks** (Sprint check, for the person shown): a Feature whose User Stories are all Closed should be Closed; a User Story whose Tasks are all Closed should be Closed; an Active Feature needs at least one Active User Story (one without any User Story is flagged too); a New Feature with an Active User Story should be Active. Each row says what is off; the first two offer the fix (Close, or Set to Active first for a New Feature), the third links to the item in Azure DevOps. Work under the absence Epic and Removed children are ignored.
- **Who new work is assigned to.** Every work item the app creates is assigned to someone — the person chosen, else the person creating it (the email on the Time Writing connection); a create without an assignee is refused before anything is sent, in the browser and the Windows app. With the role right **Create work items for other people** (Admin → People & roles → Role rights; by default Admin, Product Owner, People Manager and Scrum Master) the confirmation lets you choose anyone in the backlog: **Bulk actions → This month's Time Writing tasks** (default: the person whose work is shown), **Backlogs → ＋ Feature / Complete children** (the Feature and all its new User Stories and Task) and **Backlogs → ＋ User Story** on a Feature / **＋ Task** on a User Story (title, Iteration Path, default: the parent's assignee) and the release view's **Create Feature** (default: you). Without it, new work is assigned to you.
- **Feature setup per Epic** (Settings → **Feature setup**, every user). Each person keeps **My setup** (Git: `feature-setup/<email>.json`, used first when *they* create a Feature) and can **Enable for everyone**, which copies their setup of an Epic into the **Shared** setup (`feature-setup.json`) used by everyone without their own. Saving needs a Git token that can write. To map a setup to an Epic: type its number in **Go to Epic #** (it does not need to be fetched), then either **Use built-in Full Release / PU** to start from the built-in stories, or open the Epic you configured and use **Copy this setup to Epic #**; save to Git. A panel shows, for the chosen Epic, which setup applies when you create a Feature: *My setup*, else *Shared*, else *Built-in*. For each Epic: the **optional User Stories** offered when a Feature is created or completed under it (title, Description, order; all ticked in the dialog, untick what is not needed) and the **default hours** (Original Estimate) of a new month Task — since v3.0.0 the only Time Writing setting of a setup. Story titles are plain text and may carry placeholders filled in at creation — `{feature}` (whole Feature title), `{program}`, `{service}`, `{version}` (its parts for “Program | Service | Release”) and `{month}` — with a live preview. The Time Writing User Story and the month Task are always created by the one rule below; the Task's hours can be changed in the dialog. An Epic without a setup keeps the PU / Full Release milestones. Saved to Git as `feature-setup.json` (shared; the last one read is used while Git is not connected).
- **Move to the current PI + Sprint**: the Sprint whose dates include today (team iterations, with its PI parent) is found from Azure; only your pending **User Stories still in a past Sprint** (finish date before today) are listed with checkboxes and moved one by one. Stories already in the current or a future Sprint, stories in an undated iteration (such as only the PI), and Features, Tasks and other types are never moved.
- **Create this month's Time Writing tasks** (with a *Without task / With task / Both* switch and *Select all / Deselect all*): for each of your pending Features (or Features holding your pending work), the app adds `<Feature> - Time Writing` if missing and a `<Month YYYY> | <Feature>` Task assigned to you. Children are re-read from Azure right before writing, so an existing task of yours is reused and never duplicated; another person's task with the same title is left alone.
Every change is confirmed first, verified by reading the item back, merged into the saved data and recorded in the audit. Only *State* and *Iteration Path* can be changed this way (also in the Windows app's proxy). Every change goes to Azure DevOps Services (dev.azure.com) only: the web app and the desktop proxy both refuse writes to an on-premises server, whatever the connection's role, and a Time Writing connection cannot be saved on one. All actions are disabled while the synthetic sample is loaded.

**Fetch at start.** Every start (opening the app, **Force Update**, reload) fetches the active Time Writing connection and the cloud read-only connections that have a PAT in this browser, once the connection setup from Git is read (not waiting for the on-prem views' data, and never more than 10 seconds for Git); it shows in the top bar as **Fetch Azure DevOps at start**, with its result or why the Time Writing connection was not fetched (no PAT here, on-premises); on-prem connections keep their own **Fetch** (on VPN, in the desktop app) or their data from Git. The ↻ button still fetches everything on demand. Only one Time Writing fetch runs at a time: pressing ↻ or Fetch while one is running (for example the one at start) joins it instead of failing with “already running”.

**My dashboard and team insights.** The app opens on **My dashboard**, for everyone. **Signed by me** (v7.21.0) counts the releases and documents you signed as Author, Reviewer or Approver, per stream and in total, for a from–to period you choose (this month, this quarter, this year or the last 12 months), with the documents behind the figures. It also shows your hours for the month against your capacity (planned, recorded, utilization, overrun and ad-hoc, and the last six months), your open work (Features, User Stories, items ready to close; each count opens My Tasks [Board] or Bulk actions) and your streams and releases (the Epics you booked on and your Features due in the month). The team's insights — Dashboard, Pulse Check, PI Review — are an access area of their own, **Team insights**, shown by default to Admin and People Manager (Admin → People & roles → Role rights to change). **Pulse Check** has a **Period**: Month as before, or a calendar **Quarter**, **Half-year** or **Year**, each against the period before: releases per stream (each release once), the change, and the work opened and closed.

**Your own views.** **Customize** on My dashboard shows, hides and reorders its sections; **Customize menu** (bottom of the sidebar) lists the pages under their menu groups: tick **Pinned** to put a page at the top of the menu, untick **In menu** to hide one you never use. The Dashboard and Pulse Check remember your period and filters. Your views are kept in the Git data repository per person (`personal-views/<work email>.json`), so they follow you to every computer; an admin can make their layout the default for everyone.

**Settings pages and sections.** Settings is its own group in the menu with one page per area — **Azure DevOps**, **Storage**, **Access**, **Feature setup**, and for roles that manage shared settings **Capacity & periods**, **Resources**, **Master data**, **Monthly pack** and **Audit**. A page with several parts shows them as sections, one at a time, chosen in the row of section buttons under the header (e.g. Azure DevOps: *Servers and PATs · Stream mapping · Other views · Read-only sources · Synthetic sample*; Storage: *Git storage · Load from Git · Shared setup in Git*; Capacity & periods: *Capacity and absence · Holidays and common activities · Period control*). The app reopens the last page and, on each page, the last section; Get started and the menu's ＋ entries open the section they are about.

**Back up and clean up the connections.** Admin → Data & sharing → *Shared setup in Git* → **Back up and clean up** (roles that manage shared settings): **Download backup** saves every connection — names, servers, projects, queries, roles; never a PAT — as a dated JSON file. **Back up and remove all connections…** first downloads that backup and saves it to Git (`azure-views-backups/`), then removes every connection and its data here and from the shared setup in Git; every other computer removes its connections at its next start. PATs stay, per server. Then add the correct connections again in Settings → Azure DevOps (each stream you set up is saved to Git; *Save connections to Git* saves the others). A backup can be restored with *Restore from Git* after copying it over `azure-views.json` (CON-88).

**Azure connections.** The **Azure DevOps** tab of **Settings** holds any number of connection sets, each with a name, what it is used for, base URL, project, PAT and an optional WIQL query, pasted from Azure DevOps (Edit query → WIQL): a flat list (only its WHERE clause is used; results are paged by ID) or a **tree** or **direct-links** query (FROM WorkItemLinks … MODE (…): sent as written, up to 20,000 links, and every work item at either end of a link is read once, parents before their children). Uses: **Time Writing** (read & write; without a query the team's Epic backlog is read, with a query its results plus their missing parents up to the Epic; one Time Writing connection is active; refreshed data is saved automatically), **Releases · DHFI** (read only; default: approved documents), **Documents · Vault** and **Reference** (read only; default: all non-removed items in the project; stored as snapshots with the app data). **Fetch all** reads the active Time Writing connection and every read-only connection one after another; nothing is written to Azure when fetching. PATs stay in the browser. As in other Azure DevOps tools, a connection has an optional **server URL** (on-prem only, e.g. `https://tfs.company.com/tfs`), an **organization / collection** (on-prem: the collection name, e.g. `DefaultCollection`) and a **project**; an empty server URL means Azure DevOps Services (`https://dev.azure.com/<organization>`). The API version is detected automatically (7.1, then 6.0 and 5.0 for older Azure DevOps Server, remembered per collection) unless one is set. **Test** checks the address, collection, project and PAT with an empty query. The team's connections — the cloud Time Writing project and the DHP on-prem collection (`https://tfsapac04.ta.philips.com/tfs`, `DHPCollection`, `DHP`) — are pre-filled (`src/connectionPresets.ts`) and listed as *Needs PAT* until saved: **Set up** opens them in the form, where the PAT is entered and any field can be changed; **Dismiss** hides one in this browser. Requests, work-item links and parent links use the connection's own collection. On-prem servers are normally reachable only from the **Windows app** on VPN: it sends requests through Chromium's network stack (Windows certificate store and proxy settings), while the browser page is usually blocked by the server's cross-origin rules or company certificate.

**Azure DevOps views.** Each connection has a **View name** (optional; when empty the Time Writing backlog is named **QMS-0025** and other connections use their connection name) and a **Show in menu** switch (on by default for Time Writing and Backlog view connections, off for release, document and reference sources). Every shown connection is its own page in the sidebar's **Azure DevOps** group (no tab row). **QMS-0025** — the active Time Writing connection — is the editable Epic → Feature → User Story → Task backlog. Every other view shows its query results: a **summary strip** (counts by State and Work Item Type, which also filter the table; counts by person; overdue = open with a passed target date; changed in the last 7 days) and a **query table** with exactly the columns of the connection query's `SELECT`, in that order, named as Azure DevOps names them (read from the project's field list), sorted by the query's `ORDER BY`; any column can be sorted by clicking its heading, all columns are searchable, and **Export CSV** saves the filtered rows. A query that selects only the ID, or a team backlog without a query, shows ID, Type, Title, State, Assigned To and Iteration Path. A **Releases** (release source) view has two tabs: **Register** (stream → release from the Area Path, name, approval date, document count, and whether the Time Writing backlog tracks the release; click a release for its documents) and **Documents** (the query table). View data is fetched read-only, saved locally, and not counted in Dashboard, Monthly Time Writing, Baselines or My Tasks [Board].

**Git storage for planning data.** Baseline rules, release scopes, the region / role / reporting-line mapping and the capacity settings (absence Epic, hours per day, thresholds, and the holidays and common activities) are kept in one JSON file (`planning-data.json` by default) in a **separate private GitHub repository**, configured under **Settings → Git storage** (owner, repository, branch, file path and a fine-grained token limited to that repository with *Contents: Read and write*). The token stays in the browser like the Azure PAT and is never written to app data, exports or audits. The file is loaded when the app starts; edits show as *Unsaved changes* on the Baselines and Settings pages until **Save to Git** commits them with a message, so the repository history records who changed which baseline and when. Saving sends the version that was loaded and is refused if the file changed in the meantime (load the latest and re-apply). Loading from Git while this browser has unsaved changes asks first and names what would be replaced. Saving is disabled while the synthetic sample is loaded. Regional holidays stay in Azure under the absence Epic. Keep the app repository free of planning data: if it is public, so is its GitHub Pages site.

**Everyone sees what is saved to Git, also with the app open** (v7.7.0). The app checks Git every 5 minutes and when you come back to its window. Newer planning data saved by someone else (capacity, calculation profiles, resources, table defaults, the match threshold) loads by itself — Storage says "Updated from Git at …" — unless you have unsaved changes; any other newer shared file (Monthly pack setup or month text, QE Mapping, Access, Feature setup, the connection setup, views) is named in a **Newer data in Git** banner with **Reload**. **Table defaults** and the **fuzzy match threshold** are now saved in the planning file too, so Save to Git shares them.

**Two people saving the same shared file both keep their change.** Saves to the historical hours, the default views (*Use as default for everyone*), the KPI tracker copy, the connection backups, the On-Demand pages and the Monthly pack template wait in a queue in the order of their time (to the second) and are each saved as their own commit, with `[saved <time>]` at the end of the commit message. Before each save the app reads the file again: if someone else saved it in between, your change is merged into theirs — by row, page, sheet or connection — and where you both changed the same entry the later save wins (on the On-Demand pages also between a change and a removal); the message says "Saved to Git — merged with a change by someone else". While more than one save waits it says "Waiting to save (N in queue)"; if Git keeps changing (3 tries), the change stays in the queue with **Retry**. The PowerPoint template cannot be merged: the later save wins, and an older one is not written ("Not replaced: a newer template saved by someone else is in Storage and is kept."). Access, the Epic / Feature setup, QE Mapping, the Monthly pack setup and month text and the planning data still refuse a save when the file changed since it was loaded.

**KPI tracker** (v7.8.0; hidden from the menu since v7.11.0). **Data Insights → KPI tracker** shows the team's KPI tracker workbook from SharePoint, read only, one sheet at a time. In the **desktop app**, paste the file's SharePoint link (Copy path) and click **Read from SharePoint**; the first time, **Sign in to SharePoint** opens a window for the company sign-in (no tenant or client ID needed, no password kept). The app only downloads the file — it never writes to SharePoint. An admin's read (Manage shared settings, Git token that can write) is saved to Git as `kpi-tracker.json`, so everyone — in the browser too, and when SharePoint cannot be reached — sees that copy, with when and by whom it was read.

**Regions, roles and regional holidays.** People are read from Azure (Assigned To on Time Writing Tasks); under **Settings → Resources** each person gets a region (India, Netherlands, US), a role (QE, QMS, CAPA, Lead, Manager), an optional people-manager flag and a "reports to" line, shown as a reporting tree (a manager without Time Writing Tasks can be typed in with **Other (type a name)…** and appears at the top of the tree, marked "not on the board"). Profiles are keyed by the Azure display name and stored with the shared app data. Regional holidays live in Azure under the absence Epic: a Feature whose title names holidays and a region (for example `Public Holidays - India`; `NL`/`Netherlands`, `US`/`USA` are recognised), with a `… - Time Writing` story and `<Month YYYY> | <Holiday>` Tasks. Each Task's hours (Original Estimate, else Completed Work, else one working day) are added as **Public holiday** absence to every person mapped to that region who has bookings in the month, instead of to the Task's assignee.

**Holidays and common activities.** Under **Settings → Capacity → Holidays and common activities**, map any Epic or Feature by its ID (it need not be fetched yet) as **Holidays** (absence) or **Common activity** (reserved time, for example PI Planning, an audit or a site audit), for **Everyone** or **Everyone in** India, Netherlands or US (the region from Settings → Resources). Every month Task under it (`October 2026 | PI Planning`) then applies to each person in scope instead of to its assignee, with the hours above; holidays count as absence and activities as reserved time, and both lower available capacity without counting as booked work. The nearest mapped item above a Task decides, so a region-specific audit Feature can sit inside an Epic mapped for everyone. Mappings are saved with the planning data in Git: press **Save to Git** on the Capacity tab so everyone who loads from Git gets them. Each mapping shows its hours and the number of people for the header month; name-based holiday Features are listed as found automatically, and mapping one replaces the name rule. Pulse Check → Last month shows the common activities per person and in the funded-hours ring; the Dashboard's capacity already has them taken off. People without a region are listed as not receiving regional holidays.

### Read-only release source and connection roles

Each ADS configuration now carries a **role**: *Time tracking (Read & Write)* — the active configuration used for Fetch preview, Refresh, Feature creation and Monthly Time Writing — or *Release source (Read only)*, which never writes. Both can be active at once. Under **Azure DevOps → Release source**, select the read-only configuration (for example the DHFI project) and paste its saved work-item query; only the query's WHERE clause is used, wrapped as `SELECT [System.Id] FROM WorkItems WHERE (…) AND [System.Id] > n ORDER BY [System.Id]` so results page safely and the Electron proxy's read-only guard still applies (tree, link and ASOF queries are rejected). Fetched documents are stored with the shared app data (`releaseSource`) and audited. **Feature milestones → Approved releases by stream** reads the release identifier from each document's Area Path (last segment below the project; optionally a capture pattern in `releaseSourceSettings.releasePattern`) and the stream from the segment above it (`releaseSourceSettings.streamSegment`, default 1), lists `Stream (n): Rel1, Rel2, …`, counts approved documents per release, and flags releases that no Feature, User Story or Task title in the time-tracking backlog mentions. The stream rule is provisional until the stream definitions are confirmed.

### Get started and Settings pop-ups

**Get started.** A new user sees a **Get started** pop-up with the few things to configure, in order, each with its live status, why it matters, how to do it and a button that opens the right Settings tab: **1** connect the shared Git storage (it brings the team's connections, Feature setup, holidays and roles), **2** check the Time Writing connection and **your work email**, **3** enter your Azure DevOps PAT, **4** fetch your data (**Fetch now**). Optional: your region and role (set by a People Manager or Scrum Master) and the release streams on the on-premises server. It opens by itself while a required step is open — until you choose *Don't show again automatically* — and the **Setup · n/4** button in the top bar reopens it.

**Work email.** Set **your work email** (as Azure DevOps shows it) under **My settings → Your work email** (click your name in the sidebar). It is a setting of its own, not part of the Time Writing connection or the stream mapping, so an update (Force Update), a sync from Git or editing a connection never changes it. It finds your work on *My Tasks [Board]*, drives the Time Writing prompts and your access role, and is assigned to the Features you create; the Stream mapping shows *Work email missing* until it is set. The email stays on your computer: it is never saved to the shared setup in Git, so nobody else gets it, and a sync from Git never changes it. If your Time Writing connection had received someone else's email from an older shared setup, the app clears it once at start and asks for your own.

**Look & feel** (profile menu → Look & feel, SET-18) gathers how the app looks on one page with a tab each: **Page layout** — every page fills the width beside the menu (also when you fold it) inside a thin border; set the margin on each side (top, right, bottom, left; default 10 / 20 / 10 / 20 px) and whether the border shows (NAV-50); **Theme and zoom** — Follow the computer, Light or Dark (the top-bar button stays and follows); **Start view and menu** — Tiles or Classic and Customize menu; **Table and chart defaults** — the shared table and chart design, for the roles allowed to change it (moved from Admin → Reports). The first three are yours, on this computer.

**Pop-ups.** In Settings, adding or editing opens a pop-up over the page: Azure DevOps connections and servers, Git storage, the capacity settings, holiday and common-activity mappings, and the Feature setup of an Epic. The page keeps the lists and a summary of the saved values. Every pop-up form reads top to bottom: one field per row, its explanation under it, Cancel and the main action at the bottom right. A click beside a pop-up with input does not close it (×, Cancel and Escape do), so nothing typed is lost; this holds for every Azure DevOps write pop-up too. Pop-ups work with the keyboard: the first field takes the focus, Tab stays inside, Escape closes it (an open list inside closes first) and the focus goes back to the button that opened it.

**All shared Feature setups.** Since v7.36.2 every Epic's setup is listed in Admin → Epic & Feature setup → **All Epic setups** (its fields, title pattern and Feature setup); open one there to see or edit it.

### Roles and access

**Admin → People & roles → Role rights** decides which menu areas each person sees and what they may do. Members are added by **choosing the person by name** from the people in the Time Writing backlog (QMS-0025); the app stores their email for you (**Other (enter an email)…** for someone not in that backlog). Who you are is the email entered on your Time Writing connection (Settings → Azure DevOps, the connection's email field — the same email new work is assigned to). It is typed in, not verified by Azure DevOps (reading it from the PAT does not work in this setup), so someone could enter a colleague's email; the roles decide what the app shows, while Azure DevOps and GitHub still decide what each token can do. The roles are kept in the Git data repository as `access.json`, next to `planning-data.json`, so only people whose GitHub token can write to that repository can change them, and every change is a commit.

| Role (default) | Sees | May |
|---|---|---|
| Tool Owner | everything | everything, including the stream mapping and its query logic, the On-Demand pages and the pages and menu groups (Admin → Pages & menu) |
| Admin | everything | everything except the stream mapping and the pages and menu groups (the On-Demand pages included) |
| Product Owner | Dashboard, I&D Board, Backlog Health, Release Details, Baselines, QE Mapping, Documentation, On-Demand (view) | work items (including bulk create and for others), baselines, QE Mapping, export, Monthly pack text |
| People Manager | Dashboard, team insights, My Work, I&D Board, Release Details, Baselines, QE Mapping, Snapshots, Documentation, On-Demand (view) | the same as Product Owner |
| Scrum Master | Dashboard, My Work, I&D Board, Backlog Health, Release Details, Documentation, On-Demand (view) | work items (also for others), export, the shared Feature setup |
| Team Member | Dashboard, My Work, I&D Board, Release Details, Documentation, On-Demand (view) | their own work items, export |

**Role rights is a permission matrix** (v7.27.0): every menu area and every action is a row, in groups — *Work items in Azure DevOps* (create, assign to others, edit fields, change state / close Features, move to a Sprint or PI, enter hours, comment, bulk create), *Release data*, *Streams*, *Setup*, *Capacity and time*, *People and access*, *Reports and sharing* and *On-Demand* — and each cell is **Allow**, **Deny** or **Not set** for a role. People listed under **Members** get everything any of their roles allows, **except what any of their roles denies: a denial wins**; *Not set* means not allowed unless another role allows it. Everyone else gets the **Everyone else** role (or nothing but Settings). Search the matrix by name; **Check access** picks a person and a permission and says whether it is allowed and which role allows or denies it. Each Settings page and section appears only with its permission; Settings stays open to everyone for their own connections and tokens. An `access.json` saved before v7.27.0 keeps every person's rights: each new permission is allowed where the old action it came from was.

- **Read-only until the roles are loaded**: until `access.json` has been read from Git storage (or a copy read earlier is kept in this browser), the app is read-only for everyone — every page is shown, but nothing can be changed, and a notice at the top says so. Connect Git storage (Admin → Data & sharing) to load the roles. When Git storage is connected and has no `access.json` yet, you may only set up the first one: **Set up roles** (in the notice, or Admin → People & roles → Role rights) starts from the table above with you as Admin; you cannot save a change that takes *Manage access* away from yourself.
- **Buttons say why they are greyed out** (CON-102): every button that changes Azure DevOps — ＋ New Feature, ＋ User Story, ＋ Task, Edit, Close, Move, saving hours, Add comment, Create Feature(s) — is disabled while the roles are not loaded, or when your role lacks the action it needs, and a line next to it (above the board for its row buttons) says why. Nothing opens that could not be sent.
- **On-Demand rights**: the menu area *On-Demand pages* and two permissions of their own — *Set up On-Demand pages (pages, columns, options)* and *Edit On-Demand data (rows)*. By default every role sees the pages and Tool Owner and Admin may set them up and edit their rows. An `access.json` saved before (permissions 3 or older) gets the same: the area for every role it lists, both permissions for its Tool Owner and Admin; once Role rights is saved again (permissions 4) what you set stays as set.
- **Pages and menu groups** (permissions 5): *Manage pages and menu groups (Tool Owner)* — create, rename, reorder, configure and remove menu groups, add, move and remove any added page and name co-owners. By default the Tool Owner only; an `access.json` saved before (permissions 4 or older) gives it to its Tool Owner only. While nobody holds the Tool Owner role, the people who manage access hold it too.
- The last roles read from Git are kept in the browser, so disconnecting Git storage does not lift them; while your email is not known yet (or cannot be read), the *Everyone else* role applies.
- This decides what the app shows and does. It is not a security boundary: what each person can read or change is still decided by their own Azure DevOps PAT, project permissions and GitHub token.

### Sharing through Git

A **separate private GitHub repository** (Admin → Data & sharing → Git storage: owner, repository, branch, data file, token — the form starts with the team's repository `ponkritz/DemandPlanningStorage`, branch `main`, so a new user adds only the token) holds:

| File | Content | Written by | Read by |
|---|---|---|---|
| `planning-data.json` | baseline rules, release scopes, region / role mapping | Save to Git (Baselines, Settings) | every app at start, Load latest from Git |
| `azure-views.json` | the connection setup — view names, queries, URLs, roles, never PATs or work emails | Settings → Views in Git → Save N connections to Git | every app at start (the default for everyone), Restore from Git |
| `azure-data/<connection>.json` | the last fetch of each on-prem view | automatically at every fresh fetch (also when the data is unchanged: the fetch time is new) | the web app at start, **Load from Git** on the view — only data fetched with the query the connection has here; data fetched with another query (an older shared setup) is not loaded |
| `windchill-data/<export>.json` | each imported Windchill export | each import | every app at start, **Load from Git** / **Load all exports from Git** |

- **Load everything from Git** (Admin → Data & sharing) loads all of it at once — planning data, the connection setup, on-prem view data, Windchill exports, access roles and the Feature setup — and lists what was loaded and what failed. Data here is replaced only by newer data from Git; connections changed here are kept.
- **Default connection setup.** At start, connections missing here are added (with the PAT of a connection to the same server, else view only); connections not changed here since the last sync follow Git; connections changed here are kept. Restore from Git or Save to Git makes them follow Git again. A connection that came from Git, was removed there and was not changed here is removed here too, with its fetched data; an empty connection file removes nothing. On-prem view data is saved to Git only with a token that can write (a read-only token gets one note, not a failed commit), a save that loses a race with another commit is retried once, and a snapshot file in Git with invalid work items or an unreadable fetch time is refused rather than loaded.
- **Removed in Git, removed here.** A connection that came from the shared setup and was removed there is removed at the next start for everyone who has not changed it.
- **One Time Writing connection.** If a backlog view reads the same project and team as the Time Writing connection, Settings → Azure DevOps says so. **Use as Time Writing** on the backlog view makes it the Time Writing connection with its own (working) PAT, removes the old one here and — with a token that can save — from the shared setup in Git together with its data file in Git, then fetches.
- **Fetch falls back to Git.** When an on-prem fetch fails or there is no PAT in the browser, the view loads its data from Git and says why and when it was fetched.
- **Tokens.** Each user needs a fine-grained GitHub token for this repository: **Contents: Read-only** for viewers (a shared read-only token is possible), **Read and write** for those who save (e.g. People Managers editing baselines). With a read-only token, Baselines is view only. Tokens stay in the browser and are never written to Git. A token cannot be kept as a GitHub secret of the app repository or in a work item: anything the app reads at run time can be read by every user.
- **Duplicates.** If there is more than one Time Writing (QMS-0025) connection, Settings → Connections offers to keep the active one and remove the others, here and in Git. Other connections reading the same server, project, role and query are removed at start, keeping the copy from the shared setup in Git, else a preset's, else the first saved; saving a new or edited connection that would duplicate a saved one is refused.

### QE Mapping

**Admin → Capacity & time → Historical hours** (roles with *Manage shared settings*) brings the hours of the months before Time Writing in Azure DevOps into the reports: **Upload Excel…** (from this computer) or **From Git storage…** (an .xlsx kept in the data repository's folder or its `history/` folder) reads the planning workbook's **TransformedData** sheet (QA/QE, Month(Date), Epic No, Stream(Features), Project / Release Title, Expected, Actual, and optionally **Feature ID**) in the browser. A row's hours count under its Feature when its Feature ID is in the fetched data (whatever its Epic No says; disagreements are listed), else under its Epic No, else under the Epic chosen for its stream. Before saving you see the rows imported, the rows not imported with their reasons (no person, no month, no hours, a month from the cut-off on), each name with the name the reports will use (matched to Azure DevOps — "Ana Costa" = "Costa, Ana" — or kept as written for people who have left) and each stream without an Epic No with the Epic to count it under. Before the **cut-off month** (default October 2026) only the history counts: Azure DevOps Time Writing Tasks of those months are left out of the reports (they stay in Azure DevOps). From the cut-off on, only Azure DevOps counts. My dashboard, the Team overview, Pulse Check and the Monthly pack include the history; pages that write to Azure DevOps never show it. The rows are kept in the Git data repository (`history-hours.json`), never in the app's source; keep the workbook itself in Storage, not in the app's repository. A row whose person is **All** applies to everyone, **All-BLR** / **All-NL** / **All-US** to everyone in that region (a public holiday under the Team Holidays and Training Epic, otherwise reserved common time). Holidays, leave and trainings can be imported too: rows whose Feature ID is the regional holiday, PTO or training Feature count as public holiday, absence or training for that person only (never spread over the region). Leave and training in one Feature are told apart by an optional **Tag** column: a row tagged **Training** or **NPRA** counts as training / NPRA, the others under the absence Epic as leave. Add people who have left in Settings → Resources (region, role, Left on) so their utilization has a capacity.

**Data & governance → QE Mapping** keeps the QE mapping Excel as a shared table in Git (`qe-mapping.json`). The table is compact (tight rows, one-line headings, narrow columns) so that more columns fit on the screen; drag the right edge of a heading to resize a column (double-click resets it, **Reset widths** resets all; kept per tab in this browser). **Upload Excel…** reads an .xlsx (or CSV) as it is — every sheet becomes a tab and its first row the columns, without knowing them in advance; dates come out as YYYY-MM-DD. Then, with a Git token that can save: click a cell to edit it, **＋ Add row**, select rows and **Delete**, **＋ Add column**, and per column (▾ menu) **Rename**, **Move left / right**, **Delete column**. Everyone can search, **Filter by column**, **Group by** up to four columns, nested (Group by … then by …, or **Then group by this** in a column menu; **Collapse all** / **Expand all**) and hide columns (**Columns (n of m)**, kept in your browser). Changes are a draft until **Save to Git**; **Export Excel** downloads every tab, **Export CSV** the current view. Old .xls files must be saved as .xlsx first; a mapping over 900 KB cannot be saved to Git.

**＋ Add row** opens a pop-up with one field per column; **Save** adds the row (first in the table) and saves the QE Mapping to Git straight away, together with any other unsaved change. The **QE Name** is chosen from the Resources list (everyone with Time Writing Tasks and everyone under Settings → Resources), in the pop-up and when you click a QE Name cell.

**Calculation profile terms** (v7.1.0). Pulse Check → Last month shows four cards — **Utilization**, **Funded Hours** [Working days × Funded hrs per day], **Absence** [Holiday + PTO …] and **NPRA Hours** [Tagged NPRA hours …] — each with only its formula in brackets. What they count comes from the default calculation profile: its capacity base (Funded Hours; the global setting is now **Funded hours per day**), the leave kinds its Absence includes and whether its NPRA Hours include Training (Admin → Capacity & time → Calculation profiles, Edit). **Names** gives each profile, built-in ones too, its own names for these figures; the cards, columns and formulas use them. Every profile can be **edited** — the built-in Current (v4) and Old Calculation too (v7.2.0); a changed built-in profile shows "Built-in, changed" and has **Reset to built-in**.

**Utilization formula** (v7.5.0). Editing a calculation profile shows its formula as a sentence — *Utilization = (Project work + Training + Other NPRA + Common activities) ÷ (Funded Hours − Absence) × 100* — and you change it by ticking terms, no typing: **Top — counts as utilized** (each figure, with where its planned hours come from) and **Bottom — Funded Hours minus** (figures taken off the capacity base, and Standard Hours). A figure is in the top or the bottom, never both. The profiles table shows the same sentence.

### On-Demand pages

**On-Demand** is a menu group of blank pages the team sets up itself, without a new release of the app. **CoNQ** (*Cost of Non-Quality*) is there from the start; people allowed to *Set up On-Demand pages* add more (**＋ Add page…**: a name and an optional description — the page is created in Git at once), **Rename page…** and **Remove page…** (it asks first, naming how many rows go with it; the file's history stays in GitHub). Each page is listed in the menu and on the Home tile by its name. Every row gets a **key** the moment it is added, e.g. `CONQ-261123-K7Q2` (the page's prefix, the date, 4 random characters), unique even when several people add rows at the same time; the prefix is set per page in **Set up columns…** and fixed once rows have keys; rows from before keys get theirs on the next save (OND-18). Every row also gets a readable **ID** — `CONQ-0001`, `CONQ-0002` … — when it is first saved to Git (until then it shows *on save*); it is the next free number, never changes and stays unique when several people save at the same time (OND-19).

- **Set up columns…** (set-up right) opens a pop-up to add, rename, reorder (↑ ↓) and remove columns. Each column has a **type** — *Text*, *Long text* (a paragraph up to 10,000 characters, shown in 3 lines in the table), *Number*, *Currency*, *Date*, *Dropdown (one value)* or *Multi-select* — and can be **Required**; a Dropdown or Multi-select has an **option list** you add to, rename, reorder and remove from in the same pop-up. A **Currency** column has a **default currency** (EUR, USD, GBP, INR, … or another 3-letter code); each row holds an amount and its currency, shown as "1,200.00 EUR". Each column can have a **Description** — how or what to fill — shown under the field in the row pop-up and behind ⓘ on the column heading (OND-22, OND-23, OND-25).
- **Nothing is lost silently.** When a change touches values already in the rows, **Save** first lists what happens and asks (**Back** / **Save columns**): a type change keeps the values (several choices become one text "a, b"); values that no longer fit are kept and marked **not in the list**, **not a number**, **not a date** or **not an amount** until someone changes them; a renamed option is renamed in every row; a removed option's values are kept and marked; only a removed column takes its values with it, and the pop-up says how many.
- **Rows** (*Edit On-Demand data*): the page is one table — search, sort, the row count, Columns, Export (Excel / CSV). **＋ Add row** and **Edit** open the row in a pop-up with a field per column (a list for a Dropdown, ticks for a Multi-select); **Remove** takes a row out. Each row records **who added it** (your work email) and **when** (columns *Added by* and *Added on*, in your time zone). Every saved change of a row is **logged automatically** — who, when and what changed (*Cost: 1,200.00 USD → 1,500.00 EUR*) — and shown as **History** in the row pop-up (Edit), newest first; the last 100 changes of a row are kept. *Last updated by* / *on* can be added with **Columns**. Export holds the ID, the values, Added by / on and Last updated by / on, not the History. When two people change the same row at the same time, the later save wins for the values and both changes stay in its History (OND-20, OND-21).
- **Save to Git**: every change is first an unsaved change of the page, shown in a bar with **Discard** and **Save to Git** (as on QE Mapping); moving to another page keeps it. The page is saved as `on-demand/<page>.json` in the Git data repository (for CoNQ `on-demand/conq.json`). Two people saving the same page keep both their changes: rows and columns are merged by their id and, where both changed the same row or column, the later save wins — a row removed by the later save stays removed. The result is listed in **Background jobs**.
- Without the rights, without Git storage that can save, or with the synthetic sample loaded ("Synthetic sample data is loaded. Saving to Git is disabled."), the page is read only: its buttons are greyed out and a line says why.
- **Insights**: every page has two tabs, **Data** (the table) and **Insights** — charts and tables of your own built from the page's rows, the same for everyone. **＋ Add chart / table** (*Set up On-Demand pages*) opens a pop-up with a live preview: a title; the type — **Bar / column** (a value per category, optionally stacked by a Dropdown or Multi-select), **Line over time** (a value per month of a Date column), **Pie / donut** (shares of the total; more than 5 categories: the 5 largest and "Other") or **Summary table** (rows by one field, optional columns by another, with totals); the measure — **Count of rows**, **Sum** or **Average** of a Number or Currency column (a Currency column is never converted or added up across currencies: the chart shows one currency at a time — the one with most rows, or the one you choose above the chart — and says which currencies it found, OND-24); the sort (largest first, or by option order / month / name); and **filters** (values of a Dropdown / Multi-select, a from / to month of a Date), stated under the chart's title. Each chart has a legend, Data labels and a **Table** view. A Multi-select row counts once in each of its values (the totals take it once); empty values and values "not in the list" show as "(none)". **Edit**, **↑ ↓** and **Remove** (it asks first) change them; like rows and columns they are saved with **Save to Git**, in the page's own file (`insights`). When a column a chart uses is removed or changed to a type that does not fit, the chart says so instead of drawing; a renamed column is simply followed.

### Pages & menu (page builder)

On-Demand page and menu changes save only after GitHub confirms that the configured data repository is private.

As a **Tool Owner** you add pages of your own and use them at once, without a new release of the app. **Admin → Pages & menu** lists every menu group and every added page.

- **Page types**: **Table** — a table you set up yourself (columns, rows, search, Export) — or **Table + Insights** — the same with the **Insights** tab of charts and summary tables. CoNQ and the On-Demand pages from before are Table + Insights pages in On-Demand, unchanged. Dashboard and Release pages for a new stream come later.
- **＋ Add page…** (on Admin → Pages & menu, **⋯** next to a group's heading in the menu, or on a page): the type, a name, an optional description, an **icon**, the **menu group** — any group that **accepts added pages**, or **＋ New group…** with its name — and optional **page co-owners**. The page is created in Git at once and opens.
- **Menu groups**: the built-in groups keep their name and place and are only **configured** — *Accepts added pages* (on for On-Demand, off for the others until you turn it on) and **co-owners**. Groups of your own (shown after On-Demand, each with a Home tile) can be renamed, reordered (↑ ↓), configured and removed once they hold no page.

Ownership is matched by your **work email** (My settings). Everything else is greyed out with the reason. All added pages are seen by the roles that see the On-Demand pages.
- **Saved in Git** as `menu-layout.json` next to the planning data (the pages' tables stay in `on-demand/<page>.json`). Two people changing the menu at the same time keep both changes: groups and pages are merged one by one, the later save wins where both changed the same thing, and co-owners added by either stay while one removed by either goes. ### Monthly locking and ad-hoc Tasks

Planning defaults to locking at the end of the 5th of the selected month (midnight UTC). Actuals for a month default to locking at the end of the 5th of the following month, so Planning for the current month and Actuals for the previous month close on the same date. Settings can explicitly lock either control or extend it independently with a documented reason. When planning is closed, Original Estimate is not editable. A month Task that first receives Completed Work after planning closes is tagged `ad-hoc`; its Original Estimate remains unavailable for edit while Completed Work remains editable until Actuals close. A month Time Writing Task **created** after planning has locked — by New Feature, Complete Feature children or Bulk actions → Create month tasks — is created with the `ad-hoc` tag; the form and the confirmation say so before Save. The Feature and User Stories are not tagged, and an existing month Task that is reused keeps its tags. These controls are enforced by the app UI and Azure write request; Azure DevOps administrators should retain their normal project-level permissions as the final source-side control.

Feature closure counts require a finished state — **Closed, Resolved, Completed or Done**, the one list every page uses (FET-23) — and a close date: the Closed Date, else the day the item entered that state (State Change Date, Resolved Date, or read from its history, FET-24), bucketed by their UTC month. Target Date determines overdue non-completed items. Feature completion is not proof of release/milestone sign-off. YoY counts describe only currently fetched backlog membership; historical coverage is not guaranteed and a zero denominator never produces a fabricated percentage. Resource totals use Assigned To on Time Writing stories, not local synthetic people. Bands and lessons remain unavailable pending explicit source mappings. No 160-hour capacity is assumed. The UI provides source-item links and a field-mapping table. No external AI integration is enabled.

Refresh Azure once after updating to populate new scheduling fields in older saved caches. Run `pnpm test:azure` for source mapping, missing/zero values, hierarchy exclusion, monthly attribution and UTC date-boundary tests. Live tenant field availability must still be verified with an authenticated refresh.

### Snapshots in Git

LTE and PI Review snapshots (Snapshots page) are separate JSON files saved to the private Git data repository of Git storage (`ponkritz/DemandPlanningStorage`), in the folder `lte-snapshots/` beside the planning data — one commit per snapshot, named `{month}-{type}-{id}.json` (SNP-04…08). A snapshot is saved only as a **new file** (an existing one is never replaced) and is reported saved only after it is read back and matches. Saving needs Git storage with a token that can write; it is off with the synthetic sample, and nothing is kept in the browser. The history lists the snapshot files in Git, newest month first, each linked to GitHub. Files are capped at 50 MB.

Each snapshot freezes **all the app data present at the moment** — the work items with their hours, the release data (release source, release views, Windchill exports, plans), capacity, people, baselines and settings (SNP-05) — with the selected month/type, author (your work email), UTC creation time and build identity. It includes saved Azure work items, not an unsaved Azure fetch preview; refresh/save source data first. Earlier snapshot payloads and credentials are excluded. Snapshot JSON is not a rendered PPT/PDF report or a normal restore-backup file. *(Snapshots used to go to a SharePoint library; SharePoint is in the backlog — see PROJECT-PLAN.md.)*

### Backlogs, columns, refresh and current iterations

The Azure fetch is strictly **the selected team's native Epic backlog**, not all items in a project or area. The default source is the supplied InD Quality Epic-backlog URL. The team embedded in a backlog URL takes precedence over the manual team field. The app reads `/{team}/_apis/work/backlogs/Microsoft.EpicCategory/workItems` for Epic membership, then follows direct parent IDs through descendants using the team's exact/child-area rules and excluding Removed items. Every child query has a parent-ID constraint. An inaccessible or empty backlog never falls back to a project-wide query. Unrelated items in the same area are not fetched. The all-project Epic option has been removed.

Fetched membership is stored with organization/project/team and exact item keys. Older unscoped caches are hidden until a verified refresh. **Save and refresh data** on a connection saves its settings and immediately fetches it. Saves that write to Azure DevOps — **Monthly Time Writing** (Save … and refresh) and **My work** (close/resolve, move to the current Sprint, create month tasks) — are followed by a full refresh of the Time Writing backlog, saved locally, so every page shows the current Azure data. Every fetch — Save and refresh, Fetch, Fetch all or Refresh from Azure, for every connection type — is saved locally (browser database, or the desktop app's own storage) without a separate save step; queries are kept with their connection settings. A refresh is **saved automatically** and **replaces the Azure cache** rather than merging old out-of-scope records back in. The one exception: when Azure returns zero work items while saved data exists, the saved data is kept and the empty result is shown as a preview that can be saved or discarded, so a wrong team or query cannot wipe the cache. Export JSON first if the previous cache is needed. This removes only cached copies, not Azure source work items, activities, effort records or other app data. A failed fetch leaves the old saved data intact. Failure to remember the PAT in small browser settings no longer aborts an otherwise valid in-memory-token fetch.

### Azure PAT profiles

Connection settings can store several named ADS configurations. Each configuration is one complete set: **Azure DevOps URL, PAT and reason**—for example **Quality Backlog Read** or **Release Work Item Write**. Select exactly one active configuration; Fetch preview and Refresh use that configuration’s URL and PAT together, while the reason is the visible audit label. Saving a preview replaces the cached Azure dataset with that selected source scope, so dashboards never silently mix different source scopes. Configurations are browser-local only and excluded from IndexedDB app data, JSON backups, snapshots, browser exports and GitHub. Use separate least-privilege tokens where possible: a read-only configuration for refresh and a Work Items (Read & Write) configuration only while creating or updating work items. Removing a configuration only removes its local copy; revoke the PAT in Azure DevOps if it should no longer work. Browser-local storage is not an enterprise secret vault, so do not share a browser profile with someone who must not use the token.

**Backlogs** (formerly Board) is a compact, expandable table following Epic → Feature → User Story → Task parent links. It filters with two multi-select drop-downs: **State** (default **New + Active**; tick more states, or none for all) and **Assigned to** (default **Me**; tick other people or **Unassigned**, or none for everyone); **Reset filters** goes back to the defaults (BKL-46). Removed items are always excluded, including parent context, level selectors and the source-details table; active descendants remain visible with a missing-parent indicator. Other ancestors outside the state filter are shown as parent context. **Refresh from Azure** reads a fresh snapshot without changing Azure DevOps; **Save fetched work items** persists that snapshot in app storage. Failed refreshes retain the previous data. This is an on-demand refresh, not a background/live subscription. On desktop, the board table fits down to the footer and scrolls on its own, including at Windows display scaling. A very short window or a phone uses page scrolling. The source-details table is its own **Source details (n)** tab next to the **QMS-0025** tab (BKL-12, BKL-45).

- **Save:** only what you changed is sent, in the background. If someone changed the item in Azure DevOps after you opened it, nothing is saved and you are asked to reopen it.
- **Moving a Feature to another PI:** the form offers to move its open User Stories to a Sprint of that PI.
- **Formatting:** a changed Description or Acceptance criteria is saved as plain text.

**Column Options** supports visibility, ordering, reset, cancel and apply. Title is required to retain hierarchy controls. Preferences are saved separately in the browser per organization/project/team and do not modify Azure DevOps or central app state. Default columns: Order, ID, Work Item Type, Title, Description, State, Story Points and Actions. Additional columns: Assigned To, Iteration Path, Area Path, Target Date, Closed Date and Tags. Description is displayed as plain text, never injected HTML. Refresh old snapshots once to populate the newly mapped Description and Story Points fields. Empty numeric values are not replaced with invented estimates. The table has a sticky header, horizontal scrolling and 200-row pagination of expanded rows to bound large-list rendering. Backlog levels promote Features, User Stories or Tasks to the top level without changing their source relationships. A Tool Owner (the right *Table, chart and page defaults*) can choose **Save for everyone**: that order becomes everyone's default, kept in the shared views defaults in Git; anyone's own **Apply** still wins in their browser, and **Reset to the team default** returns to it (BKL-47).

Order is a displayed root-row number, not a write to Azure backlog priority.

### Large browser datasets and storage recovery

Full app data now uses **IndexedDB**, not the small synchronous localStorage snapshot. PATs, connection configuration and column preferences remain separate small browser settings. On first use of this version, an empty IndexedDB imports the previously saved `demand-planning-mvp-v1` snapshot; the old copy is retained, not deleted. Once IndexedDB contains data it takes precedence, so an older legacy snapshot cannot overwrite a newer database. A database read failure or malformed backup blocks startup rather than replacing saved data with demo records. No initial seed is saved before hydration completes.

Autosaves are debounced and serialized; a save is confirmed only on IndexedDB transaction completion. Failed/aborted saves retain the previous committed data, show a persistent warning, offer direct JSON backup and retry controls, and warn on closing with pending saves. Browser privacy policy, disk limits, eviction and clearing site data can still affect persistence. This is browser-local storage, **not** a multi-user central database or a guarantee of unlimited space.

If the old version displays a storage-full warning, keep that tab open and first use **Snapshots → Portable data → JSON**. Open the updated version separately, then use **Snapshots → Browser storage & backup recovery** to select the JSON file, review counts and confirm replacement. Restore does not write to Azure DevOps. Wait for a confirmed browser save before closing the old tab. Backups contain app records but not the PAT; protect them as internal data. In-memory-only changes in an old tab cannot be recovered automatically after that tab is reloaded or closed.

`pnpm test:azure` runs both Azure integration checks and storage tests, including a 14,000-item synthetic backlog, legacy migration, failed reads, serialization, aborts and backup validation. `tests/browser-storage-preview.html` is a local-only UI fixture using a separate synthetic test database; it never opens the real app database.

New Features are assigned to the work email (required) saved on the active Time Writing connection (not the app's local demo user, and not the PAT identity GUID, which Azure DevOps does not accept as Assigned To). The assignment is verified after Feature creation. Tokens remain outside exported app state.

Opening the creation form reads team iterations and the project iteration tree. Dated leaf iterations containing today's UTC date are treated as Sprint candidates; their nearest dated ancestor is the PI. Team-configured Sprint candidates take precedence. Start and finish days are inclusive. A unique pair is preselected; overlapping branches require explicit selection and missing dates/nesting block creation until corrected in Azure settings. The mapping is shown for review: **Feature → PI; optional User Stories → Sprint; Time Writing User Story → the setup's Iteration Path, else the project root; Time Writing Task → project root**. Dates are rechecked before a write. Existing Feature/child iterations are not silently changed during completion; conflicting existing children require manual review in Azure.

No production data, tenant identifiers, access tokens, client secrets or employee information belong in Git. The local adapter persists synthetic development records in browser storage.

Shared data is kept in the private Git data repository (Git storage); every save is a commit and is refused if the file changed since it was loaded — except the historical hours, default views, KPI tracker copy, connection backups and the Monthly pack template, which are queued and merged (GIT-17). *(The SharePoint central storage is in the backlog.)*
